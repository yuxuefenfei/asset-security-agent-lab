# 第 7 课：从教学 Demo 升级成企业级系统

## 0. 先明确当前不是生产版

本项目特意没有安装或部署 MySQL、Redis、RabbitMQ、pgvector，也没有接真实漏洞扫描器。这样是为了保证首次学习的环境成本极低。下面是合理的升级顺序，而不是声称已经实现的功能。

## 阶段 1：领域模型与持久化

- 当前已有 H2、PO/Mapper 和三个类型化 Repository；接入真实数据时按生产数据库与资产授权模型调整。
- MySQL 保存资产、漏洞、分析任务、工单草稿、审批记录与审计日志。
- 建立 `(tenant_id, asset_id)` 联合索引，跨租户读写始终带过滤。
- PostgreSQL/pgvector 保存知识 chunk；使用 `document_id` + 版本控制去重。
- 建议状态机：`CREATED -> ANALYZING -> PENDING_REVIEW -> APPROVED -> TICKET_CREATED -> VERIFYING -> CLOSED`，异常分支单独处理。

## 阶段 2：可靠性与异步处理

- 重计算分析任务由 HTTP 同步改为 `POST /tasks` 返回 `taskId`，由后台工作线程或消息消费者消费（此处的「后台」指你的自建服务，不是本对话后台任务）。
- 使用 MQ（RabbitMQ/Kafka）解耦扫描事件和分析任务。消费者必须幂等。
- 任务表记录状态、错误类型、重试次数、开始/结束时间和模型版本。
- 对模型和工具设置各自超时、重试上限、熔断，记录失败原因。
- 使用 `traceId` 关联任务、LLM 请求、工具调用和工单事件。

## 阶段 3：更真实的 AI Agent

- 对 Tool 加入显式的领域约束，例如查询扫描任务结果、归并相同漏洞实例。
- 让 Agent 自动判断需要哪个 **只读**工具；不要把确定性业务流程改成无控制循环。
- 使用可靠的检索增强：精确 CVE 匹配 + 文档过滤 + Embedding + 重排。
- 建立 30~100 条高质量评测集：检查工具选择、引文正确性、越权、工单建议准确率。
- 设定调用成本预算、P95 延迟和错误预算，定期人工抽样。

## 阶段 4：MCP 标准化

- 现有的 Feign/REST Service 仍然保留，MCP Server 只作为 **AI 工具协议适配层**。
- 只包装多个 Agent 真实需要共同复用的能力，明确职责和工具版本。
- 对 MCP `tools/list` 和 `tools/call` 设置认证授权、速率限制、审计和参数校验。
- 写契约测试，保证 Server 工具 Schema 与实际实现一致。
- 根据组织/权限边界决定是否拆成资产、漏洞和知识三个 MCP Server，不要为了微服务数量而拆。

## 阶段 5：连接真实工单与扫描器

- 通过 Webhook/消息队列接收扫描器上报，而不是让大模型调用任意公网扫描命令。
- 漏洞实例键应含 `tenant_id`、资产标识、检测规则、端口/服务实例等必要维度，避免误合并。
- 经授权的 Java 服务创建草稿，人工审批后才创建正式工单；数据库唯一约束防重，Outbox 保存待投递事件并重试，外部接收方仍需按业务键幂等。
- 工单修复后需要真实扫描器复检或人工验证，模型不能自行宣称漏洞已修复。

## 各阶段架构选择

| 阶段     | 应该增加的能力                      | 不急着引入的东西       |
|----------|-------------------------------------|------------------------|
| 入门     | 本地 Tool + 权限边界 + trace        | Kubernetes、多 Agent   |
| 可展示   | 模型 Tool Calling + 引文 + 人工审批 | 大量异构中间件         |
| 企业应用 | 数据持久化、日志、IAM、异步化       | 为简单工具全部改 MCP   |
| 平台化   | MCP 工具中心、评测、指标治理        | 所有业务操作都交给 LLM |

## 常见构建问题

**Maven 命令不存在**：JDK 与 Maven 是两个工具，需额外安装 Maven 3.9+。`offline-lab` 和 Spring 示例都使用 Maven 构建；离线核心打包后的 JAR 运行时仅需要 JDK 21。

**Maven 无法下载依赖**：检查网络、代理、公司 Maven Central 镜像或可信 Artifactory/Nexus 制品库。仓库没有打包第三方依赖或不明来源的
JAR。

**Ollama 连接失败**：确认 `ollama serve` 正在运行，`OLLAMA_BASE_URL` 是否正确，模型是否已经 `ollama pull`。

**模型返回不了工具调用**：检查模型是否支持 `tools`、模型版本和兼容 API 能力。有些模型仅生成文字而不返回结构化工具请求。

**Spring AI 代码报版本不匹配**：请保证 Spring AI 和 Spring Boot 版本配套；本项目固定 Spring AI 1.1.0 + Boot 3.5.7。Spring
AI 2.x 的部分属性、API 和执行循环与 1.x 不同，请按目标版本官方文档调整。

**MCP Client 无法连接**：确认先启动 8080 核心服务，再启动 8082 MCP Server，再启动 8083 Agent 的 `mcp` profile；不能在 8083
同时启动两份 Agent。

## 关于对代码交付的校验说明

2026-10-12 的核验环境使用 JDK 21.0.4 和 Maven 3.9.6，已完成离线源码编译、协议/HTTP 回归测试，以及两个 Spring 模块的 Maven 测试和可执行 JAR 打包。Spring 回归包括 5 项 Agent 测试与 2 项真实 MCP HTTP 集成测试。

这项结论针对仓库固定的 Spring AI 1.1.0 + Spring Boot 3.5.7，不表示它们是最新版本，也不代表真实 Ollama 模型质量或生产能力已验证。完整核验范围及复现命令见 [09-核验记录.md](09-核验记录.md)。

从仓库根目录执行 `mvn package` 统一构建共享契约和三个服务，再使用
`java -jar spring-ai-workshop/agent-app/target/agent-app-1.0.0.jar` 或 MCP 对应 JAR 启动。根目录 `mvn verify`
会自动运行打包后的跨服务测试；`spring-boot:run` 不应用于没有主类的聚合父工程。
